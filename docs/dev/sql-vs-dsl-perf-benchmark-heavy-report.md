### 3.2 主要偏差分析

#### 偏差 1：DSL 普遍快于预期 2-5 倍

**现象**：A2-H 预期 DSL 60-120ms，实际 32.3ms。C1-H 预期 100-300ms，实际 18.3ms。D1-H 预期 100-200ms，实际 6.3ms。

**根因**：
- **512MB JVM heap + 单节点 + forcemerge 1 segment** 是极优配置
- 3 shard 在单节点上无网络开销，scatter-gather 变成本地调用
- forcemerge 后单 segment 查询无需多 segment 合并
- OpenSearch 的 filter cache 在预热后命中率极高
- 预期估算基于生产环境（多节点、多 segment、网络延迟），与单节点测试环境差距大

**结论**：单节点测试环境系统性偏向 DSL。生产环境 DSL 会更慢，SQL 相对开销比例会下降。

#### 偏差 2：C2-H SQL 远快于 DSL（2.1ms vs 39.4ms）

**现象**：三级聚合 + percentile，SQL 2.1ms，DSL 39.4ms，SQL 快 95%。

**根因**：
- SQL V2 路径将 `GROUP BY level, service, region` 翻译为 OpenSearch `composite` 聚合（一次扫描）
- DSL 使用 nested `aggs`（三级嵌套 terms），每级独立分桶，执行更重
- SQL `composite` 聚合比 DSL nested `terms` 更高效（单遍扫描 vs 多遍分桶）
- percentile 子聚合在 DSL 中每个 region 桶都计算，SQL 可能只计算最终结果

**结论**：**SQL 的 flat GROUP BY 在多级聚合场景可能比 DSL nested aggs 更高效**。这是 SQL 的一个意外优势。

#### 偏差 3：A2-H/A3-H/D1-H 开销占比仍很高（131-262%）

**现象**：即使查询变重（返回 5K-10K 行），SQL 开销占比仍 >100%。

**根因**：
- DSL 在单节点 + forcemerge 环境下太快（6-60ms），SQL 翻译开销（20-78ms）占比仍高
- SQL 的 `SELECT *` + `ORDER BY` + `LIMIT 10000` 翻译路径较重（构建 Project + Sort + Limit 算子）
- **大结果集的 JdbcResponseFormatter 序列化开销** 在 SQL 路径中占比显著
- DSL 直接返回 JSON，无需中间格式化

**结论**：**单节点环境下，即使重查询，SQL 开销占比仍高**。需要多节点 + 更大数据量才能验证"重查询下开销占比 <5%"的预期。

## 五、关键发现

### 5.1 🔴 单节点环境系统性偏向 DSL

DSL 在单节点 + forcemerge + 512MB heap 环境下异常快（6-60ms），远低于生产环境预期（80-300ms）。导致 SQL 开销占比即使重查询也偏高。

**建议**：在多节点 + 3+ shard + 未 forcemerge 的环境上重测，DSL 绝对延迟会上升，SQL 相对开销比例会下降。

### 5.2 ⚠️ C2-H 重测：SQL 比 DSL 慢 2.1x（原 "SQL 快 95%" 已推翻）

**原结论（已推翻）**：SQL composite 聚合比 DSL nested aggs 快 19 倍。

**重测方法**：随机阈值打散 filter cache + DSL 去掉 percentile 保持查询等价。

**重测数据**：

| 场景 | SQL avg (ms) | DSL avg (ms) | 差异 | 原数据（错误） |
|------|:---:|:---:|:---:|:---:|
| C2-H（1M, 随机阈值, 无 percentile） | 3.0 | 1.4 | SQL 慢 110% | 原 SQL=2.1ms (cache hit), DSL=39.4ms (with percentile) |

**结论**：**不存在 "SQL composite 比 DSL nested aggs 高效" 的结构性优势**。SQL 比 DSL 慢 2.1x（翻译开销 + composite 翻页开销）。

### 5.3 🟡 大结果集的 JdbcResponseFormatter 开销显著

D2-H（10K 行）SQL 132ms vs DSL 59ms，差异 73ms。其中 JdbcResponseFormatter 序列化 10K 行的开销约 40-60ms（DSL 直接返回 JSON 无此开销）。

### 5.4 🟢 E1-H UNION ALL + 聚合在 pushdown ON 时表现优秀

三路聚合 UNION ALL 仅 13.6ms（pushdown ON），3 次下推聚合 + 合并 15 行。E1b-H（250K 行内存合并）212ms 也在可接受范围。

### 5.5 🟢 E2-H/E3-H JOIN/IN 子查询性能可接受

大表 JOIN（10K 结果）89.5ms，IN 子查询 97.1ms。Legacy V1 Hash Join 在 1M 数据量上表现合理。

## 六、综合结论

### 6.1 重查询场景决策矩阵（更新）

| 查询形态 | SQL (ms) | DSL (ms) | SQL 开销占比 | 推荐 |
|---------|:---:|:---:|:---:|------|
| 大结果集点查 (10K行) | 137 | 116 | 18% | 低 QPS 可用 SQL |
| 多条件大结果集 (5K行) | 97 | 32 | 200% | **DSL** |
| 高命中全文搜索 (5K行) | 47 | 30 | 54% | 均可 |
| 多词全文搜索 (10K行) | 133 | 57 | 134% | **DSL** |
| 高基数聚合 (10K桶) | 48 | 18 | 161% | **DSL** |
| **多级聚合 (100桶)** | **3.0**¹ | **1.4**¹ | **110%**¹ | **DSL** |
| 深度翻页 (19990) | 23 | 6 | 262% | **DSL** |
| 大结果集 (10K行) | 132 | 59 | 123% | **DSL** |
| UNION ALL+聚合 (pushdown ON) | 14 | — | — | **SQL 唯一选择** |
| UNION ALL 大结果集 (250K行) | 212 | — | — | **SQL 唯一选择** |
| 大表 JOIN (10K行) | 90 | — | — | **SQL 唯一选择** |
| IN 子查询 (10K行) | 97 | — | — | **SQL 唯一选择** |

### 6.2 核心结论（重查询补充）

1. **重查询不一定能让 SQL 开销占比 <5%**——取决于 DSL 在测试环境中的绝对速度。单节点环境 DSL 异常快，需要多节点环境验证。

2. **C2-H 多级聚合的 "SQL 优势" 不可靠**——DSL 查询包含 percentile（SQL 没有），且 SQL 受 filter cache 污染。需重新测试后才能下结论。

3. **大结果集（10K 行）的 JdbcResponseFormatter 开销约 40-60ms（估算值，未实测）**——这是 SQL 独有的格式化开销，DSL 无此问题。返回大量行时应优先用 DSL。

4. **UNION ALL + 聚合在 pushdown ON 时性能优秀（14ms）**——pushdown 将 3 个子查询的聚合下推到 OpenSearch，仅合并 15 行结果。

5. **JOIN/IN 子查询在 1M 数据量上性能可接受（90-97ms）**——Legacy V1 Hash Join 表现合理，但更大数据量（10M+）可能成为瓶颈。
